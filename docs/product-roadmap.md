# SayRight 产品路线图

## 当前定位

SayRight 是一个面向中文母语者的 AI 英文表达纠错工具。核心价值主张：**把中式英文改成自然英文**。

不做单词背诵、不做语法教材、不做课程体系。只解决一个问题：中文母语者写英文时，怎么让它更像母语者写的。

## 当前网页版能力（v0.7）

| 模块 | 说明 |
|------|------|
| AI 纠错 | 输入任意英文，DeepSeek API 返回修正、自然表达、中文解释、替代表达 |
| 场景化改写 | 支持通用、日常聊天、工作邮件、职场沟通、学术表达、简历优化、社交媒体 7 种场景 |
| 错误库 | 保存纠错记录到 localStorage，支持掌握标记、复习计数、场景筛选 |
| 错误画像 | 按标签统计错误频率，可视化展示前 5 类错误 |
| 复习系统 | 按掌握状态筛选，支持复习模式，记录复习次数和时间 |
| 参考例句库 | 5000 条 Tatoeba 中英对照句子，支持等级/场景筛选和搜索 |
| 产品化框架 | 设置面板（API Key 说明）、支持开发入口、开发路线展示 |

## 产品路线

### v1.0 桌面端 App — 下一个里程碑

- **目标用户**：有高频英文写作需求的职场人士和学术用户
- **核心场景**：
  - 在任意应用中写作英文，快捷键唤起 SayRight 窗口，纠错后直接粘贴回去
  - 长期积累个人错误库，可回顾和复习
  - 使用自己的 DeepSeek API Key，无调用次数限制
- **技术方案**：Electron（详见 `docs/desktop-plan.md`）
- **限制与风险**：
  - Electron 包体较大（~150MB），对非技术用户下载门槛较高
  - 需要处理 macOS/Windows 双平台兼容
  - 全局快捷键可能与系统或其他应用冲突
  - 自带 API Key 意味着用户需要自己去 DeepSeek 注册获取 Key，有一定门槛

### v1.5 浏览器插件

- **目标用户**：在网页中写作英文的用户（Gmail、Notion、GitHub Issues 等）
- **核心场景**：
  - 在 Gmail 写邮件时，选中英文直接纠错替换
  - 在 Notion/Google Docs 中写作时一键优化表达
  - 在 GitHub/GitLab 中写 Issue/PR 描述时改英文
- **限制与风险**：
  - 浏览器插件权限审核（Chrome Web Store / Firefox Add-ons）
  - 不同网页的 DOM 结构差异大，适配成本高
  - 插件形态的 UI 空间有限，不适合展示复杂错误库
  - 依赖网页端后端或浏览器内置 API Key 存储

### v2.0 手机端 App

- **目标用户**：移动办公场景下的英文写作需求
- **核心场景**：
  - 修改工作消息、邮件草稿
  - 出国旅行或留学时的快速表达检查
- **限制与风险**：
  - 手机端文字输入和编辑体验不如桌面端高效
  - App Store 审核周期长（iOS 尤其）
  - 双端原生开发成本高（React Native / Flutter 可降低但仍有维护成本）
  - 移动端输入法类产品有更重的隐私合规要求

### v3.0 输入法形态探索

- **目标**：在最底层解决中文母语者英文输入问题
- **核心场景**：
  - 用户在任何 App 中输入英文，输入法实时提示更自然的表达
- **限制与风险**（此阶段面临最严峻挑战）：
  - 输入法可以读取所有按键（隐私敏感），需要强信任基础
  - iOS 第三方输入法权限受限，体验不如系统输入法
  - 需要本地模型或极低延迟的云端调用
  - 如果出错会严重影响用户输入体验
  - 商业化和隐私保护的矛盾
- **当前判断**：长期探索方向，不会在 v1.0/v2.0 阶段投入。需要等待端侧 AI 模型成熟和隐私方案明确后再评估。

## 为什么暂时不做

### 账号系统

- 当前所有数据保存在 localStorage，不需要后端数据库
- 加入账号系统需要：注册/登录、密码加密、数据库、会话管理、GDPR/个保法合规
- 一个个人开发者无法同时承担这些工程和安全成本
- 桌面版可以用本地文件存储代替账号同步
- 如果将来需要跨设备同步，优先考虑 iCloud/本地文件导出导入，而非自建云服务

### 在线支付系统

- 支付系统需要企业资质、支付渠道审核、税务处理、退款机制
- 网页版暂时以免费试用形态存在，AI 成本由开发者承担
- 桌面版通过用户自带 API Key 回避平台承担 AI 调用成本的问题
- 如果未来需要商业化的付费版（用户不想自己注册 API Key），再考虑接入 Stripe/Lemon Squeezy 等低门槛方案
